# Tradeoffs

## Backend First

The backend was built first because the core domain requirements depend on reliable data modeling, employee CRUD, salary aggregation, and seeding 10,000 employees.

Tradeoff:

- Faster validation of core business logic.
- UI still needs to be built to satisfy the full end-to-end requirement.

## Users And Employees Split

Employee full names are stored on the `users` table, while employment details are stored on `employees`.

Benefits:

- Keeps identity/authentication-ready data separate from HR data.
- Allows future login/auth flows without redesigning employee records.

Costs:

- Employee queries need joins/eager loading for full names and emails.
- Creating an employee requires an existing user.

## UUIDs For API Lookup

Employee detail/update/delete routes use UUIDs.

Benefits:

- Avoids exposing sequential IDs.
- Safer public API shape.

Costs:

- Slightly more complexity in validation and lookup.
- Requires UUID indexes.

## Soft Delete For Employees

Employee delete uses soft delete and marks the employee inactive.

Benefits:

- Preserves historical records.
- Prevents deleted employees from being counted as active.

Costs:

- Queries must be clear about whether deleted records should appear.
- Reporting requirements may later need explicit historical views.

## Dashboard Aggregates In SQL

Dashboard metrics are calculated with database aggregate queries.

Benefits:

- Avoids loading 10,000 rows into PHP memory.
- Keeps dashboard endpoints responsive.
- Easier to validate with deterministic tests.

Costs:

- Some aggregate result typing differs between SQLite and MySQL.
- More advanced analytics may need database-specific tuning.

## Seeder Rerun Strategy

The seeder deletes and recreates only records generated by the seeder.

Benefits:

- Engineers can rerun `db:seed` safely.
- Manually created records are not wiped.
- Deterministic seeded email/code patterns avoid collisions.

Costs:

- Seeded records receive new UUIDs each run.
- If external data references seeded records, those references would need rebuilding.

## PATCH Is Partial, PUT Is Full

`EmployeeUpdateRequest` treats `PATCH` fields as optional but validates any fields that are present. `PUT` requires the full payload.

Benefits:

- Matches common HTTP semantics.
- UI can send small partial updates.

Costs:

- Slightly more validation complexity.

## No Auth For Main APIs

Employee and dashboard APIs currently use throttling middleware but do not require authentication.

Benefits:

- Faster assessment/demo setup.
- Avoids blocking frontend work on auth flows.

Costs:

- Not production-ready for sensitive salary data.
- Auth and authorization should be added before real deployment.

Recommended future state:

- Add login.
- Protect employee and dashboard routes with `auth:sanctum`.
- Add role-based authorization for HR Manager/Admin access.

## Tests Use SQLite In Memory

Tests run on SQLite `:memory:`.

Benefits:

- Fast.
- Deterministic.
- Easy for reviewers to run.

Costs:

- Decimal serialization can differ from MySQL.
- Some SQL behavior can differ by database engine.

Mitigation:

- Tests compare numeric aggregate values with flexible numeric assertions where needed.

## Comments Kept Selective

Comments were added only around important logic:

- UUID route lookup.
- Dynamic filtering.
- Aggregate dashboard queries.
- Seeder safety/performance.
- PUT vs PATCH behavior.

Benefit:

- Code remains readable without comment noise.
